# V0.1 踩坑记录

## 概述

V0.1 是游戏Demo的最小可用版本，实现了基础登录、进入场景、位置移动功能。在开发过程中遇到了一些典型问题，本文档记录这些问题及解决方案。

---

## 踩坑 1：多业务线程读取出错

### 问题描述

在 Tars 服务端中，`GDImp` 的成员变量（如 `_sessions`、`_players`）被多个业务线程同时访问，导致数据竞争（Data Race）或读取到不完整的数据。

### 原因分析

Tars 框架默认使用多线程处理请求，每个请求可能在不同的业务线程中执行。如果成员变量没有做线程安全保护，直接读写会导致：
- 读取到正在写入的数据（数据竞争）
- 迭代器失效（如在遍历 `unordered_map` 时有其他线程修改）

### 解决方案

使用 `std::mutex` + `std::lock_guard` 对共享数据进行保护：

```cpp
std::unordered_map<tars::Int64, std::string> GDImp::_sessions;
std::mutex GDImp::_sessionMutex;

// 读取时加锁
{
    lock_guard<mutex> lock(_sessionMutex);
    auto it = _sessions.find(sessionId);
    if (it == _sessions.end()) {
        return -1;
    }
    openId = it->second;
}
```

### 注意事项

- 锁的粒度要适中，避免锁内执行耗时操作
- 只读操作也需要加锁，防止与写操作冲突
- 考虑使用 `std::atomic` 对简单类型进行原子操作

## 踩坑 2：sessionId 与 userId 映射错误

### 问题描述

最初设计时，错误地认为 `sessionId` 可以直接作为 `playerId` 使用。这导致：
- 玩家登出后重新登录，`sessionId` 变化，但玩家数据丢失
- 无法实现"玩家位置持久化"功能

### 原因分析

`sessionId` 是每次登录时动态生成的会话 ID，用于身份验证；而 `playerId` 是玩家的唯一标识，应该与玩家的 openId 绑定。

错误的映射：
```cpp
// 错误：sessionId 就是 playerId
playerId = sessionId;
```

正确的映射：
```cpp
// 正确：通过 openId 查找或创建 playerId
std::unordered_map<std::string, tars::Int64> _openIdToPlayerId;
```

### 解决方案

引入 `openId -> playerId` 的映射表：

```cpp
// 登录时
if (_openIdToPlayerId.exists(openId)) {
    playerId = _openIdToPlayerId[openId];  // 复用已有 playerId
} else {
    playerId = generatePlayerId();
    _openIdToPlayerId[openId] = playerId;
}

// 进入场景时
if (_players.exists(playerId)) {
    // 复用已有位置
} else {
    // 创建新玩家
}
```

### 效果

- 玩家登出后重新登录，`playerId` 保持不变
- 玩家数据（如位置）可以持久化保留

## 踩坑 3：客户端未读取服务端返回的 self

### 问题描述

在测试"位置持久化"功能时，发现 `enter` 命令后位置显示为 `(0, 0)`，而不是上次登出前的位置。

### 原因分析

接口设计时已经修改为 `enterScene` 返回 `PlayerInfo self`，包含玩家的完整信息（包括位置）。但客户端代码未正确解析返回值。

错误的做法：
```cpp
// 只关心返回值，未读取 self
tars::Int32 ret = _prx->enterScene(_sessionId, _playerId, players);
if (ret == 0) {
    cout << "[EnterScene] Success!" << endl;
    // 忘记从 self 中获取位置
}
```

### 解决方案

客户端需要接收并解析 `self` 参数：

```cpp
PlayerInfo self;
vector<PlayerInfo> players;
tars::Int32 ret = _prx->enterScene(_sessionId, _playerId, self, players);
if (ret == 0) {
    _x = self.x;  // 从 self 中读取位置
    _y = self.y;
    cout << "[EnterScene] Current pos: (" << _x << ", " << _y << ")" << endl;
}
```

## 踩坑 4：move 命令需要先进入场景

### 问题描述

测试时发现，直接调用 `move` 命令会返回 `ret=-1`（失败）。

### 原因分析

服务端 `move` 方法会检查玩家是否已进入场景（是否在 `_players` 映射中）。如果玩家还未 `enterScene`，则直接 `move` 会失败。

服务端校验逻辑：
```cpp
auto it = _players.find(playerId);
if (it == _players.end()) {
    return -1;  // 玩家还未进入场景
}
```

### 正确的测试流程

```
login player001
enter        # 先进入场景
move 10 999  # 再移动
logout
login player001
enter        # 位置已持久化
```

## 踩坑 5：Proto 共享文件同步

### 问题描述

修改 `.tars` 接口后，服务端和客户端生成的代码不同步，导致序列化/反序列化出错。

### 解决方案

使用共享的 Proto 目录：
- 路径：`/home/tarsproto/GameDemo/GameDemoScene/`
- 服务端和客户端都引用该目录下的生成代码

每次修改接口后，需要重新部署服务端，并确保客户端引用最新的 Proto 文件。

## 总结

| 踩坑点 | 根因 | 解决方案 |
|--------|------|----------|
| 多线程读取出错 | 共享数据未加锁 | `std::mutex` + `lock_guard` |
| sessionId/userId 映射错误 | 混淆会话ID和玩家ID | 引入 `openId->playerId` 映射 |
| self 未读取 | 客户端未解析返回值 | 接收 `PlayerInfo self` 参数 |
| move 失败 | 未先 enterScene | 按正确顺序执行命令 |
| Proto 不同步 | 接口修改后未同步 | 使用共享 Proto 目录 |
