# V0.2.5 - 数据职责边界重构

> **目标**: 修复 LobbyServer 数据职责混乱问题，实现单一数据源原则

## 问题分析

### 当前架构问题

```cpp
// LobbyServer.h 第48行
std::map<tars::Int32, std::set<tars::Int64>> _scenePlayers;  // ❌ 冗余数据
```

```
┌─────────────────────┐          ┌─────────────────────┐
│   LobbyServer       │          │   SceneServer       │
├─────────────────────┤          ├─────────────────────┤
│                     │          │                     │
│  _scenePlayers ❌   │  ←──────▶│  GlobalPlayers ✅   │
│  (场景玩家列表)      │   两份相同数据  │  (场景玩家列表)   │
│                     │          │                     │
└─────────────────────┘          └─────────────────────┘
```

**问题**：
- `_scenePlayers` 与 SceneServer 的 `GlobalPlayers` 数据重复
- 任何更新失败都导致两边数据不一致
- Lobby 不应关心"场景内有哪些玩家"

### 数据职责混乱

| 数据 | 应由谁持有 | 当前由谁持有 |
|------|-----------|-------------|
| connId ↔ playerId 映射 | LobbyServer | LobbyServer ✅ |
| playerId → current | 应该是 SceneServer | LobbyServer ❌ |
| sceneId → players | SceneServer | LobbyServer ❌ |

---

## 改进方案

### 设计原则

**单一数据源原则 + 最小状态原则**：
- SceneServer 是场景数据的唯一权威
- LobbyServer 只负责路由和转发，**不持有任何业务状态**
- SceneServer 调用 LobbyServer 时传入需要通知的玩家列表，LobbyServer 根据连接状态执行推送

### 通信流程

**核心原则**：
1. SceneServer 不直接与客户端通信，所有推送必须通过 LobbyServer 转发
2. SceneServer 调用 LobbyServer 时传入**需要通知的玩家列表**
3. LobbyServer 根据玩家列表查询连接状态，执行 PushCallback

#### 进入场景流程
```
Client → Lobby: enterScene
Lobby  → Scene: enterScene (同步RPC)
Scene  : 添加到 GlobalPlayers，存储 current
Lobby  → Client: enterSceneRsp

Scene  → Lobby: notifyPlayerEnter(notifyList, player)
           └─ notifyList = Scene 内除新玩家外的所有 playerId
Lobby  : 遍历 notifyList，查询 connId，执行 PushCallback
```

#### 移动广播流程
```
Client → Lobby: move
Lobby  → Scene: move (同步RPC)
Scene  : 更新位置
Scene  → Lobby: notifyPlayerMove(notifyList, playerId, x, y, z)
           └─ notifyList = Scene 内其他玩家的 playerId（由 Scene 自己计算）
Lobby  : 遍历 notifyList，查询 connId，执行 PushCallback
```

#### 离开场景流程
```
Client → Lobby: leaveScene
Lobby  → Scene: leaveScene (同步RPC)
Scene  : 从 GlobalPlayers 移除
Scene  → Lobby: notifyPlayerLeave(notifyList, playerId)
Lobby  : 遍历 notifyList，查询 connId，执行 PushCallback
```

#### 2. Push.tars 接口设计

```cpp
// Push.tars - SceneServer 调用 LobbyServer 的推送接口
interface Scene2LobbyPush
{
    // 玩家进入场景，通知其他玩家
    // notifyList: Scene 内除新玩家外的所有 playerId
    int onPlayerEnter(vector<long> notifyList, long playerId, int sceneId, PlayerInfo player);
    
    // 玩家移动，通知其他玩家
    // notifyList: Scene 内其他玩家的 playerId
    int onPlayerMove(vector<long> notifyList, long playerId, int sceneId, float x, float y, float z);
    
    // 玩家离开，通知其他玩家
    // notifyList: Scene 内其他玩家的 playerId
    int onPlayerLeave(vector<long> notifyList, long playerId, int sceneId);
};
```

**接口设计说明**：
- SceneServer 负责计算 `notifyList`，LobbyServer 只负责根据列表推送
- LobbyServer **不持有**场景玩家状态，只持有 `_playerCurrents` 用于推送

#### 3. LobbyServer 实现推送回调

```cpp
// LobbyImp.cpp - 接收 SceneServer 的通知，执行推送
// 核心: 遍历 notifyList，从 _playerCurrents 获取连接并推送

// 辅助函数：遍历 notifyList 推送
template<typename Notify>
void pushToNotifyList(const vector<tars::Int64>& notifyList, const Notify& notify, 
    const function<void(tars::TarsCurrentPtr, int, const Notify&)>& pushFunc)
{
    for (tars::Int64 targetPlayerId : notifyList) {
        auto currentIt = g_app.findPlayerCurrent(targetPlayerId);
        if (currentIt == g_app.playerCurrentsEnd()) continue;
        
        pushFunc(currentIt->second, 0, notify);
    }
}

// 接收玩家进入通知
tars::Int32 Scene2LobbyPushImp::onPlayerEnter(tars::TarsCurrentPtr _current_,
    const vector<tars::Int64>& notifyList, tars::Int64 playerId, tars::Int32 sceneId, 
    const PlayerInfo& player)
{
    PlayerEnterNotify notify;
    notify.player = player;
    notify.timestamp = TNOW;
    
    pushToNotifyList(notifyList, notify, [](tars::TarsCurrentPtr current, int ret, const PlayerEnterNotify& n) {
        Lobby2ClientPush::async_response_push_onPlayerEnter(current, ret, n);
    });
    
    return 0;
}

// 接收玩家移动通知
tars::Int32 Scene2LobbyPushImp::onPlayerMove(tars::TarsCurrentPtr _current_,
    const vector<tars::Int64>& notifyList, tars::Int64 playerId, tars::Int32 sceneId, 
    tars::Float x, tars::Float y, tars::Float z)
{
    PlayerMoveNotify notify;
    notify.playerId = playerId;
    notify.x = x;
    notify.y = y;
    notify.z = z;
    notify.timestamp = TNOW;
    
    pushToNotifyList(notifyList, notify, [](tars::TarsCurrentPtr current, int ret, const PlayerMoveNotify& n) {
        Lobby2ClientPush::async_response_push_onPlayerMove(current, ret, n);
    });
    
    return 0;
}

// 接收玩家离开通知
tars::Int32 Scene2LobbyPushImp::onPlayerLeave(tars::TarsCurrentPtr _current_,
    const vector<tars::Int64>& notifyList, tars::Int64 playerId, tars::Int32 sceneId)
{
    PlayerLeaveNotify notify;
    notify.playerId = playerId;
    notify.timestamp = TNOW;
    
    pushToNotifyList(notifyList, notify, [](tars::TarsCurrentPtr current, int ret, const PlayerLeaveNotify& n) {
        Lobby2ClientPush::async_response_push_onPlayerLeave(current, ret, n);
    });
    
    return 0;
}
```

**说明**：
- 开发者只需实现 `onPlayerEnter/Move/Leave`，`async_onPlayerEnter/Move/Leave` 由 Tars 框架自动生成
- LobbyServer 只持有 `_playerCurrents`，**不持有**场景状态
- `pushToNotifyList` 辅助函数使代码保持优雅

## 架构原则

**内部服务不应暴露给外部客户端 + 最小状态原则**：
- SceneServer 作为内部逻辑服务，只与 LobbyServer 通信
- 所有对外通信必须通过 LobbyServer
- SceneServer 调用 LobbyServer 时传入需要通知的玩家列表
- LobbyServer 只做路由转发，不持有任何场景业务状态
- 保持清晰的通信边界，提高系统安全性
