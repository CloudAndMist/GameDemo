### .tars 接口设计

> **语法规范**（参考 DBServer 实现）：
> - `const` 定义：`const int NAME = value;`
> - `enum` 定义：`enum Name { ... };`
> - `struct` 定义：`struct Name { 0 require type field; ... };`
> - `interface` 定义：`interface Name { int method(type param); };`
> - 参数格式：`index require/out type name`（索引、必选/可选、类型、参数名）
> - 回调接口：`interface Callback { int callbackMethod(out type param); };`（int 返回 + out 参数）

```tars
// ========== GameDemoBase/GameDemoBase.tars ==========
```

#### 2. 连接生命周期（工业规范版）

> **设计原则**：不维护应用层 Session，直接利用 Tars 框架的连接管理能力
> - `connectionId`：Tars 原生连接标识，连接建立时自动分配，断开时自动失效
> - `playerId`：业务层玩家唯一标识，登录后由 DBServer 分配并返回

```cpp
客户端                           服务端 (LobbyServer)
   │                               │
   │────── 1. TCP连接 ─────────────▶│ Tars 分配 connectionId
   │◀───── 连接成功 (connId) ─────│ 记录: connId -> 空
   │                               │
   │────── 2. Login ──────────────▶│ 验证 openId，申请 playerId
   │◀───── playerId ──────────────│ 记录: connId -> playerId
   │                               │
   │────── 3. CreateRole ─────────▶│ DBServer 创建角色
   │◀───── roleInfo ──────────────│
   │                               │
   │────── 4. EnterScene ─────────▶│ 路由到目标 SceneServer
   │                               │ 记录: playerId ↔ sceneId
   │                               │
   │◀───── 5. 推送: 其他人移动 ──────│ SceneServer 推送
   │◀───── 6. 推送: 其他人进入 ──────│
   │                               │
   │────── 7. Move ───────────────▶│ 更新位置
   │                               │▶ SceneServer 广播
   │                               │
   │────── 8. 断线 ───────────────▶│ LobbyServer 检测到断连
   │                               │ 清理: connId -> playerId
   │                               │ 通知 SceneServer 玩家离线
```

**关键设计说明**：

| 设计点 | 传统方案 (Session) | 工业规范方案 (无 Session) |
|--------|-------------------|--------------------------|
| 连接标识 | sessionId (需生成/存储/过期) | connectionId (Tars 原生) |
| 身份验证 | 每次请求携带 sessionId 校验 | connId 隐式绑定 playerId |
| 内存管理 | 需定期清理过期 session | connId 断开即失效，无需维护 |
| 安全性 | session 可能被伪造 | Tars 底层保证连接可信 |
| 性能 | 多一次 map 查找 | 直接映射 |

**LobbyServer 连接管理模块（简化版）**：

```cpp
// ConnectionManager.h - 无 Session 版本
class ConnectionManager {
public:
    // 登录时绑定
    void bindPlayer(uint32_t connId, int64_t playerId, const string& openId);
    
    // 断线时解绑
    void unbindConnection(uint32_t connId);
    
    // 通过 connId 获取 playerId
    int64_t getPlayerId(uint32_t connId);
    
    // 通过 playerId 获取 connId
    uint32_t getConnectionId(int64_t playerId);
    
    // 心跳更新（可选，用于监控）
    void updateHeartbeat(uint32_t connId);
    
    // 踢出玩家
    void kickPlayer(int64_t playerId, const string& reason);

private:
    // 连接信息: connId -> PlayerSession (轻量结构)
    std::unordered_map<uint32_t, PlayerSession> _connections;
    
    // 反向索引: playerId -> connId
    std::unordered_map<int64_t, uint32_t> _playerToConn;
    
    // 定时清理过期连接（心跳超时）
    void cleanupExpiredConnections();
};

// 简化后的数据结构
struct PlayerSession {
    int64_t playerId;
    string openId;
    int64_t lastHeartbeat;
    // 不需要 sessionId，connectionId 就是天然标识
};
```

#### 3. 推送机制设计（架构 A：LobbyServer 统一推送）

> **核心设计**：Client 只连接 LobbyServer，所有推送经过 LobbyServer 转发
> - Client 长连接 LobbyServer，不断开
> - LobbyServer 持有所有在线玩家的 connId
> - SceneServer 处理业务后返回给 LobbyServer，LobbyServer 负责推送

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           连接架构 (架构 A)                             │
├─────────────────────────────────────────────────────────────────────────┤
│  LobbyServer (端口 10001)                                              │
│    - 长连接：Client 一直保持连接                                        │
│    - 管理：connId ↔ playerId 映射                                       │
│    - 职责：登录、大厅、路由转发、推送回调                                 │
│                                                                         │
│  SceneServer (端口 10002+)                                              │
│    - 无需维护 Client 连接                                                │
│    - 内部 RPC 服务                                                      │
│    - 处理场景业务，返回结果给 LobbyServer                                │
└─────────────────────────────────────────────────────────────────────────┘
```

**推送流程（完整路径）**：

```
玩家 A Move           LobbyServer          SceneServer          玩家 B
   │                      │                     │                   │
   │──── Move ────────────▶│──── Move ─────────▶│                   │
   │                      │                     │                   │
   │                      │◀─── Rsp + 广播 ─────│                   │
   │                      │                     │                   │
   │                      │──── onPlayerMove ──────────────────────▶│
   │◀─── Rsp ────────────│                     │                   │
```

**为什么 LobbyServer 统一推送**：

| 设计 | 推送路径 | 优点 | 缺点 |
|------|----------|------|------|
| **LobbyServer 统一推送（推荐）** | Scene → Lobby → 玩家 | 连接统一管理、安全性高 | 多一跳（<1ms 内网） |
| SceneServer 直连 | SceneServer → 玩家 | 路径最短 | 连接分散、无法统一管控 |

#### 3. 为什么不需要应用层 Session？

1. **Tars 框架天然具备连接管理能力**
   - 每个 TCP 连接分配唯一的 `connectionId`
   - 连接断开时 Tars 自动清理，无需业务层维护

2. **登录状态通过 connId → playerId 映射保持**
   - 登录时建立映射，客户端后续请求携带 playerId
   - 服务端验证 playerId 所属 connId 是否匹配当前连接

3. **安全性更强**
   - 传统 Session 可能被盗用伪造
   - connectionId 无法伪造，必须是真实 Tars 连接

4. **运维更简单**
   - 无需考虑 Session 过期策略
   - 无需 Session 同步（多节点部署）

#### 5. 客户端连接策略（架构 A）

```cpp
class GameClient {
    uint32_t _connId;        // Tars 连接标识
    int64_t _playerId;       // 登录后获取
    std::string _openId;     // 本地保存用于重连
    GameCallbackPrx _callbackPrx;  // 回调代理
    
    // 登录成功后注册回调
    bool login(const string& openId) {
        // 1. 调用登录接口
        int ret = _lobbyPrx->login(openId, _playerId);
        if (ret != 0) return false;
        
        // 2. 创建回调对象并注册到 LobbyServer
        // ⚠️ 重要：登录成功后立即注册回调，否则无法接收推送
        _callbackPrx = new GameCallbackImp();  // 实现 GameCallback 接口
        _lobbyPrx->registerCallback(_playerId, _callbackPrx);
        
        // 3. 启动心跳保活
        startHeartbeat();
        
        return true;
    }
    
    // 心跳定时器
    void startHeartbeat() {
        _heartbeatTimer = std::thread([this]() {
            while (_running && _connected) {
                std::this_thread::sleep_for(std::chrono::seconds(30));
                if (_running && _connected) {
                    sendHeartbeat(_playerId);  // 通过 LobbyServer 连接发送
                }
            }
        });
    }
    
    // 断线重连 (指数退避)
    void reconnect() {
        int retry = 0;
        while (_running && !_connected) {
            int delay = std::min(60, 1 << retry);  // 1s, 2s, 4s... 最大60s
            std::this_thread::sleep_for(std::chrono::seconds(delay));
            
            // 重连到 LobbyServer
            if (tryConnectLobby()) {
                // 重新登录验证
                if (relogin(_openId)) {
                    // ⚠️ 重新注册回调
                    _callbackPrx = new GameCallbackImp();
                    _lobbyPrx->registerCallback(_playerId, _callbackPrx);
                    // 重连成功，恢复场景状态
                    restoreSceneState();
                }
            }
            retry++;
        }
    }
};
```

**重连流程说明**：
1. 客户端本地保存 `openId`
2. 断线后重连到 LobbyServer
3. 调用 `login(openId)` 重新获取 `playerId`
4. ⚠️ **重新注册回调**（重要！）
5. 调用 `reenterScene(playerId)` 恢复场景状态

### 服务端推送机制 (Server Push)

#### 问题：服务端如何主动推送消息给客户端？

Tars 本身是**请求-响应**模式，不支持服务端主动推送。有以下几种方案：

#### 方案对比

| 方案 | 优点 | 缺点 | 推荐场景 |
|------|------|------|----------|
| **Tars 双向连接** | 与 Tars 集成好 | 实现复杂 | Tars 生态 |
| **WebSocket** | 成熟、广泛支持 | 需要额外服务 | Web 客户端 |
| **Protobuf RPC** | 高效、跨语言 | 需要独立服务 | 高性能游戏 |
| **轮询** | 简单 | 延迟高、资源浪费 | 低频更新 |

#### 推荐：Tars PushCallback 回调模式

> **重要**：根据 Tars 官方 PushCallbackDemo 示例，推送回调接口**使用 `int` 返回类型 + `out` 参数**，不使用 `oneway`！

```tars
// Scene.tars - PushCallback 双向通信接口

module GameDemo {

    // 客户端回调接口 (由客户端实现，服务端调用)
    // 参考官方 PushCallbackDemo (Push.tars) 语法
    interface GameCallback {
        int onPlayerMove(out PlayerMoveNotify notify);
        int onPlayerEnter(out PlayerEnterNotify notify);
        int onPlayerLeave(out PlayerLeaveNotify notify);
        int onHeartbeat(out int64 serverTime);
    };
    
    // Lobby 服务接口 (客户端调用)
    interface LobbyServant {
        // 登录成功后注册回调
        int registerCallback(1 require int64 playerId, 2 require GameCallback* callback);
        
        // 心跳
        int heartbeat(1 require int64 playerId);
    };
    
    // 场景服务主接口
    interface SceneServant {
        // 进入场景时传递回调
        int enterScene(1 require int64 playerId, 
                       2 require int sceneId,
                       3 require GameCallback* callback,
                       4 out int ret, 5 out string msg,
                       6 out PlayerInfo self, 7 out vector<PlayerInfo> players);
        
        // 移动
        int move(1 require int64 playerId, 
                 2 require float x, 
                 3 require float y,
                 4 require float z,
                 5 out int ret, 6 out string msg);
        
        // 心跳
        int heartbeat(1 require int64 playerId);
    };
};
```

> **Tars PushCallback 机制说明**（参考官方 PushCallbackDemo）：
> 1. 回调接口使用 `int` 返回类型和 `out` 参数，参考官方 `Push.tars` 示例
> 2. 服务端调用 `async_xxx()` 方法异步调用客户端回调
> 3. 客户端实现 `GameCallback` 接口
> 4. LobbyServer 保存 `playerId -> GameCallbackPrx` 映射用于推送

#### 服务端推送实现（架构 A）

```cpp
// SceneImp.cpp - SceneServer 只处理业务，返回结果给 LobbyServer
class SceneImp : public SceneServant {
private:
    // 场景内玩家: playerId -> PlayerInfo
    std::unordered_map<int64_t, PlayerInfo> _scenePlayers;
    
public:
    // 玩家移动
    tars::Int32 move(tars::Int64 playerId, tars::Float x, tars::Float y, tars::Float z) {
        // 1. 更新位置
        auto& player = _scenePlayers[playerId];
        player.x = x;
        player.y = y;
        player.z = z;
        
        // 2. 构造通知（包含需要推送的玩家列表）
        PlayerMoveNotify notify;
        notify.playerId = playerId;
        notify.x = x;
        notify.y = y;
        notify.z = z;
        notify.timestamp = TC_Common::now2ms();
        
        // 3. 收集场景内其他玩家的 playerId
        std::vector<int64_t> otherPlayerIds;
        for (auto& kv : _scenePlayers) {
            if (kv.first != playerId) {
                otherPlayerIds.push_back(kv.first);
            }
        }
        
        // 4. 返回给 LobbyServer，由 LobbyServer 负责推送
        return makeMoveRsp(notify, otherPlayerIds);
    }
};

// LobbyImp.cpp - LobbyServer 负责推送
class LobbyImp : public LobbyServant {
private:
    // connId ↔ playerId 映射
    std::unordered_map<uint32_t, PlayerSession> _connections;
    std::unordered_map<int64_t, uint32_t> _playerToConn;
    
    // playerId -> CallbackPrx (Client 回调)
    std::unordered_map<int64_t, GameCallbackPrx> _callbacks;
    
public:
    // 收到 SceneServer 的推送请求
    void onPlayerMove(int64_t playerId, const PlayerMoveNotify& notify,
                      const vector<int64_t>& otherPlayerIds) {
        // 遍历其他玩家，通过 LobbyServer 推送
        for (int64_t otherId : otherPlayerIds) {
            auto it = _callbacks.find(otherId);
            if (it != _callbacks.end()) {
                // 异步推送，不阻塞主流程
                it->second->async_onPlayerMove(notify);
            }
        }
    }
};
```

#### 客户端接收实现

```cpp
// 客户端回调实现类
class GameCallbackImp : public GameCallback {
public:
    void onPlayerMove(const PlayerMoveNotify& notify) override {
        // 更新本地其他玩家位置
        updateOtherPlayerPos(notify.playerId, notify.x, notify.y, notify.z);
        cout << "[Sync] Player " << notify.playerId 
             << " moved to (" << notify.x << ", " << notify.y << ")" << endl;
    }
    
    void onPlayerEnter(const PlayerEnterNotify& notify) override {
        // 添加新玩家
        addPlayer(notify.player);
        cout << "[Sync] Player " << notify.player.roleName << " entered" << endl;
    }
    
    void onPlayerLeave(const PlayerLeaveNotify& notify) override {
        // 移除玩家
        removePlayer(notify.playerId);
        cout << "[Sync] Player " << notify.playerId << " left" << endl;
    }
};
```

#### 推送时序图（架构 A：LobbyServer 统一推送）

```
玩家 A                    LobbyServer          SceneServer          玩家 B
   │                          │                     │                   │
   │──── 1. Login ────────────▶│                     │                   │
   │◀── playerId ─────────────│                     │                   │
   │                          │                     │                   │
   │──── 2. registerCallback ──▶│  保存 playerId→CallbackPrx            │
   │◀── 成功 ─────────────────│                     │                   │
   │                          │                     │                   │
   │──── 3. Move ─────────────▶│──── Move ─────────▶│                   │
   │                          │                     │                   │
   │                          │◀─── Rsp ───────────│                   │
   │                          │                     │                   │
   │                          │──── onPlayerMove ──────────────────────▶│
   │◀─── Move Rsp ───────────│                     │                   │
```

**说明**：
1. 玩家登录成功后，LobbyServer 返回 `playerId`，**不断开连接**
2. 客户端一直保持与 LobbyServer 的连接
3. Move 请求发送到 LobbyServer，LobbyServer 转发给 SceneServer
4. SceneServer 处理后返回结果，LobbyServer 查找其他玩家的 connId 并推送

### 断线处理（架构 A：LobbyServer 统一管理）

```cpp
// LobbyServer 端：连接断开时自动调用
void LobbyImp::onConnectionClose(uint32_t connId) {
    auto it = _connections.find(connId);
    if (it == _connections.end()) return;
    
    PlayerSession session = it->second;
    
    // 1. 从连接映射移除
    _playerToConn.erase(session.playerId);
    _connections.erase(connId);
    
    // 2. 通知 SceneServer 玩家离线
    sceneProxy->onPlayerOffline(session.playerId, session.sceneId);
    
    // 3. 广播玩家离开通知给其他在线玩家
    PlayerLeaveNotify notify;
    notify.playerId = session.playerId;
    notify.timestamp = TC_Common::now2ms();
    broadcastToOnlinePlayers(notify);  // LobbyServer 查找其他玩家的 connId 并推送
}
```

> **注意**：LobbyServer 检测到断连后，SceneServer 也会收到通知，清理场景内的玩家数据

| 风险 | 应对措施 |
|------|----------|
| MySQL 连接池配置 | 根据玩家数量调整连接池大小 |
| 服务间调用延迟 | 使用 Tars 异步调用优化 |
