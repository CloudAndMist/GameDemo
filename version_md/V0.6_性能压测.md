## 架构说明

### 客户端调用链路
```
Bot ──(TARS RPC)──> LobbyServer ──(TARS RPC)──> SceneServer
                            │                         │
                            └──(TARS RPC)──> DBServer ─┘
                                                  │
                                            ┌─────┴─────┐
                                         DBServant    KVServant
                                         (MySQL)      (Redis)
```

> **关键**: Bot 只与 LobbyServer 交互，不直接连接 SceneServer。所有请求通过 LobbyServantPrx 调用。

### 移动广播链路
```
Bot A ──move──> LobbyServer ──move──> SceneServer ──AOI计算──> Scene2LobbyPush
                    ↑                                        │
                    └── onPlayerMove ── Lobby2ClientPush ←───┘
                            │
                    Bot B/C/D... 收到广播
```

> **广播扇出风险与缓解**: 当前 AOI 为场景级广播，单场景 N 人同时移动 1次/秒，总推送量 = N×(N-1) 次/秒。单场景 1000 人时理论峰值 ≈ 100万次推送/秒。**缓解策略**: Bot 进入场景后先执行一次初始分散移动，将位置随机分布到 [0~999, 0~999, 0] 的 1000×1000 坐标空间，使 Bot 尽可能分散。后续随机移动步长控制在 ±5 以内，保持位置分散。实际广播量取决于 AOI 视距范围，空间分散后可有效降低单次移动的广播扇出。

### Bot 登录完整流程
```
1. login(username, password)              // 获取 playerId + sessionKey
   └── hasCharacter = true (已预创建角色，跳过创角)
2. registerPush(playerId)                 // 注册推送回调，否则收不到广播
3. tars_set_push_callback(PushCallback)   // 设置 Push 回调处理类
4. startHeartbeat(3)                      // 每3秒心跳，否则被判定掉线
5. enterScene(playerId, sessionKey, 1)  // 进入场景 (统一 scene 1)
6. scatterMove()                        // 初始分散移动: 随机 [0~999, 0~999, 0]，分散到坐标空间
```

> **说明**: 压测账号通过 SQL 预创建 (Step 2)，注册+创角一步到位，Bot 登录时 `hasCharacter=true`，无需调用 `registerAccount` 和 `createCharacter`。所有 Bot 统一进入 scene 1，进入后先执行一次随机分散移动将位置分布到 1000×1000 坐标空间，再开始正常随机移动。

### 移动延迟测量
```cpp
// 使用异步调用 + 回调计时
class BotMoveCallback : public LobbyServantPrxCallback {
public:
    BotMoveCallback(chrono::steady_clock::time_point sendTime, LoadBot* bot)
        : _sendTime(sendTime), _bot(bot) {}
    
    virtual void callback_move(tars::Int32 ret, const MoveRsp& rsp) {
        auto latencyMs = chrono::duration_cast<chrono::milliseconds>(
            chrono::steady_clock::now() - _sendTime).count();
        _bot->recordMoveLatency(latencyMs);
    }
    
private:
    chrono::steady_clock::time_point _sendTime;
    LoadBot* _bot;
};

// 发送
void LoadBot::randomMove() {
    // 初始分散: 首次移动跳到随机位置 [0~999, 0~999, 0]
    if (!_scatterDone) {
        _curX = rand() % 1000;
        _curY = rand() % 1000;
        _scatterDone = true;
    } else {
        // 正常随机移动: 步长 ±5，保持分散
        _curX = max(0.0f, min(999.0f, _curX + (rand() % 11 - 5)));
        _curY = max(0.0f, min(999.0f, _curY + (rand() % 11 - 5)));
    }
    float z = 0;  // 固定 z=0
    
    MoveReq req;
    req.playerId = _playerId;
    req.sessionKey = _sessionKey;
    req.x = _curX; req.y = _curY; req.z = z;
    
    auto sendTime = chrono::steady_clock::now();
    _lobbyPrx->async_move(new BotMoveCallback(sendTime, this), req);
}
```

> **延迟语义**: 此处测量的是"请求→响应"延迟（含 Lobby 转发 + Scene 处理 + 返回），单向移动延迟约为其一半。端到端广播延迟（Bot A 移动 → Bot B 收到 Push）需额外的时间同步机制，V0.6 暂不实现。

### Push 广播回调
```cpp
class BotPushCallback : public GameDemo::Lobby2ClientPushPrxCallback {
public:
    BotPushCallback(LoadBot* bot) : _bot(bot) {}
    
    // 玩家进入场景
    virtual void callback_onPlayerEnter(tars::Int32 ret, const PlayerEnterNotify& notify) {
        _bot->recordPushNotify(PushType::ENTER);
    }
    
    // 玩家移动 - 统计广播接收量
    virtual void callback_onPlayerMove(tars::Int32 ret, const PlayerMoveNotify& notify) {
        _bot->recordPushNotify(PushType::MOVE);
    }
    
    // 玩家离开场景
    virtual void callback_onPlayerLeave(tars::Int32 ret, const PlayerLeaveNotify& notify) {
        _bot->recordPushNotify(PushType::LEAVE);
    }
    
    // 玩家掉线
    virtual void callback_onPlayerOffline(tars::Int32 ret, const PlayerOfflineNotify& notify) {
        _bot->recordPushNotify(PushType::OFFLINE);
    }
    
    // 玩家重连
    virtual void callback_onPlayerOnline(tars::Int32 ret, const PlayerEnterNotify& notify) {
        _bot->recordPushNotify(PushType::ONLINE);
    }
    
private:
    LoadBot* _bot;
};
```

```cpp
struct PerformanceMetrics {
    // 连接指标
    int totalConnections;
    int activeConnections;
    
    // QPS 指标
    double loginQPS;
    double moveQPS;
    double sceneChangeQPS;
    
    // 延迟指标 (基于异步回调测量)
    double moveAvgLatency;    // 平均延迟
    double moveP50Latency;    // P50 延迟
    double moveP99Latency;    // P99 延迟
    double moveMaxLatency;    // 最大延迟
    
    // 广播指标
    int64_t pushMoveCount;    // 收到的移动广播数
    int64_t pushEnterCount;   // 收到的进入广播数
    int64_t pushLeaveCount;   // 收到的离开广播数
    double pushPerBotPerSec;  // 每个 Bot 每秒收到的广播数
    
    // 服务端指标
    double cpuUsage;
    double memoryUsage;
    int onlinePlayers;
};

// P99 计算方法
double calcP99(vector<int64_t>& latencies) {
    if (latencies.empty()) return 0;
    sort(latencies.begin(), latencies.end());
    size_t idx = (size_t)(latencies.size() * 0.99);
    return (double)latencies[min(idx, latencies.size() - 1)];
}
```

```sql
CREATE PROCEDURE create_bot_accounts()

    DECLARE v_name VARCHAR(64);

        SET v_name = CONCAT('Bot', LPAD(i, 4, '0'));

            UNIX_TIMESTAMP() * 1000,           -- create_time
            0                                  -- last_login_time
        );
        
        SET i = i + 1;

END//
```

| 30次/s | 705,350 | 33 | 25 | 121 | 3,912 | 5,931,740 | 197.72 |

> **500 Bot 结论**: 20次/s 以内延迟平稳（p99≤30ms），30次/s 出现明显过载（p99=121ms，max=3.9s）。服务端安全频率上限约 20次/s。

> **1000 Bot 结论**: 5次/s 以内延迟稳定（p99≈81ms），10次/s 开始过载（p99=416ms，avg=135ms）。瓶颈在广播推送量而非请求频率——1000人同场景，每人每次 move 的广播开销固定，频率翻倍延迟不变，但超过服务端处理能力后急剧恶化。

### 关键发现

1. **广播推送是主要瓶颈**: 1000 Bot 3次/s 和 5次/s 的 p99 几乎相同（81ms），说明延迟由广播推送量决定，而非请求频率
2. **线性扩展区间**: 500 Bot 20次/s 和 1000 Bot 5次/s 的总 QPS 接近（500×20 vs 1000×5），延迟也都在可接受范围内
3. **非线性恶化**: 超过服务端处理能力后延迟急剧上升，不存在渐变过渡区

## 潜在风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| AOI 广播风暴 | 单场景人数过多时推送量爆炸 | 统一 scene 1，初始分散移动到 [0~999,0~999,0]，后续小步长 ±5 保持分散 |
